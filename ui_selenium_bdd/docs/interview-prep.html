02

Questions Architecture

Q

Pourquoi Selenium et pas Playwright ou Cypress ?

Choix justifié par le contexte Java/Maven de l'équipe. Selenium 4 apporte le CDP natif, WebDriverManager élimine la gestion manuelle des drivers, et l'intégration TestNG + Allure est mature. Playwright aurait été mon choix pour un nouveau projet greenfield en Node — il est plus rapide en headless. Mais Selenium reste le standard en mission Java et le plus demandé dans les appels d'offres entreprise.
Q

Pourquoi TestNG plutôt que JUnit 5 comme runner Cucumber ?

TestNG donne accès à ISuiteListener et IAnnotationTransformer — deux interfaces que j'utilise concrètement : AllureSuiteListener pour calculer les KPIs après la suite, et RetryTransformer pour injecter automatiquement le retry sur tous les scénarios. L'auto-discovery via META-INF/services élimine les annotations @Listeners sur le runner — aucune modification de fichier existant pour activer un nouveau listener.
Q

C'est quoi le ThreadLocal dans TestContext ?

En exécution parallèle, chaque thread Cucumber gère son propre scénario. Un état partagé en static provoquerait des race conditions — le thread 1 écraserait les données du thread 2. ThreadLocal<Map<String, Object>> garantit que chaque thread a son propre espace mémoire isolé. Le cleanup se fait dans @After pour éviter les memory leaks entre scénarios.
Q

Comment fonctionne ton AllureSuiteListener ?

Il implémente ISuiteListener, enregistré via META-INF/services/org.testng.ITestNGListener — zéro annotation sur le runner.

• onStart() : écrit categories.json et copie le dossier history/ pour alimenter le widget Trend
• onFinish() : lit les résultats depuis ISuiteResult, calcule 18 KPIs (Pass Rate, Fail Rate, durée, smoke, critical), les écrit dans environment.properties

Résultat : les 3 widgets Allure — Environment, Categories, Trend — sont alimentés automatiquement sans toucher au build ou à la config Allure.
Q

Pourquoi java.net.http.HttpClient et pas RestAssured pour l'API Setup ?

Décision architecturale consciente : zéro dépendance ajoutée au pom.xml. java.net.http est built-in depuis Java 11, disponible partout où Java 17 tourne. RestAssured est excellent mais ajoute une dépendance et un DSL. Pour une feature ponctuelle comme le API Setup Pattern, la built-in suffit. J'ai ajouté un SSLContext trust-all pour les proxies corporate qui interceptent le TLS — problème réel rencontré et résolu.
Q

Comment fonctionne le retry sur les tests flaky ?

Deux classes : RetryAnalyzer implémente IRetryAnalyzer — compteur par instance, max 2 retries. RetryTransformer implémente IAnnotationTransformer — at transform time, injecte RetryAnalyzer sur chaque méthode @Test via annotation.setRetryAnalyzer(). Les deux sont enregistrés via META-INF/services.

Résultat : tout scénario flaky est relancé automatiquement jusqu'à 2 fois, sans modifier le runner ni les step definitions. Allure marque les retried scenarios avec un badge spécifique.

03

Questions Agents IA

Q

C'est quoi concrètement un « agent » dans ton framework ?

Un script Python autonome qui orchestre : exécution Maven, lecture des résultats Allure, appel LLM via Groq, action (commit git, notification Slack, ticket Jira). L'agent n'est pas un RAG ni un assistant conversationnel — c'est un pipeline déterministe avec une étape LLM pour les décisions non-structurées.

Exemple : bug-agent.py triage lit les échecs JSON, demande au LLM de les classifier (Product Defect / Infrastructure Issue / Framework Error), structure la réponse en JSON typé, crée les tickets.
Q

Pourquoi 6 patterns LLM différents ?

Chaque pattern correspond à un niveau de fiabilité nécessaire :

• chat — génération de code Gherkin : une réponse suffit
• chat_cot — Root Cause Analysis : raisonnement pas-à-pas auditable
• chat_structured — triage et vote release : JSON typé, validé par schema
• chat_confident — prédiction quality gate : score de confiance, rejet sous 70%
• chat_self_consistent — analyse flaky : 3 appels, consensus majoritaire
• chat_adversarial — vérification cohérence : un LLM génère, un second critique

Le choix du pattern est proportionnel au coût d'une mauvaise décision.
Q

Tu utilises Groq — c'est quoi et pourquoi pas OpenAI ?

Groq est une inference platform ultra-rapide basée sur des LPU (Language Processing Units). Latence ~100ms vs ~800ms sur OpenAI GPT-4. Pour des agents dans un pipeline CI où on veut un résultat en moins de 5 secondes, c'est décisif.

Modèle : llama-3.3-70b-versatile — open source, 128k context window, comparable à GPT-4 sur les tâches de code. En production client, on peut switcher vers Azure OpenAI si la politique de sécurité l'exige — changement de 2 lignes dans PromptStore.
Q

C'est quoi ton PromptStore ?

Système de versioning des prompts. Chaque prompt est un fichier JSON avec version, template, pattern, created_at. PromptStore lit le fichier, sélectionne la dernière version, remplace les variables {{"{{"}}placeholder{{"}}"}}.

Avantages : rollback d'un prompt si les résultats régressent, comparaison A/B entre versions, traçabilité de quel prompt a produit quel résultat dans les traces JSONL.
Q

Comment tu évites que l'agent LLM hallucine et crée de faux tickets ?

Trois mécanismes :

1. Pattern chat_structured avec JSON schema — le LLM doit respecter un format précis, sinon on rejette et on repose la question
2. Pattern chat_self_consistent — 3 appels indépendants, consensus majoritaire. Une hallucination isolée est éliminée
3. Circuit breaker dans observability-agent.py — si le taux d'erreur LLM dépasse 30%, les agents passent en mode dégradé (actions manuelles uniquement)

Aucune hallucination ne peut déclencher une action irréversible sans validation.

04

Patterns QA Senior

Q

C'est quoi l'API Setup Pattern et pourquoi c'est important ?

Les préconditions de test ne passent jamais par l'UI.

Exemple concret : pour tester "ajout de todo", il faut un user connecté.
• Approche junior : UI Signup dans un @Before — lent (3-5s), fragile (si Signup a un bug, tous les tests Todo échouent)
• Approche senior : POST /api/v1/users/register en 300ms — le user existe en base, on va directement au login

Isolation totale : si Signup est cassé, les tests Todo continuent de passer. Ce pattern réduit les faux positifs et divise par 3 le temps de précondition.
Q

Comment tu gères le test data teardown ?

Le teardown browser est en place (fermeture Chrome, cleanup cookies). Pour le teardown métier (suppression du user créé en précondition), le pattern est implémenté dans Hooks.java — il suffit que l'API expose un endpoint DELETE.

Sur QACart (app de démo publique), cet endpoint n'existe pas — c'est une limite de l'app, pas du framework. En mission sur une vraie app, j'ajoute la méthode deleteUser(token) dans le client API et le hook s'en charge automatiquement. Estimation : 2 heures une fois l'accès DB obtenu.
Q

Comment tu garantis la qualité du framework lui-même ?

quality-agent.py analyze lance une analyse automatique : pass rate, flaky rate, doublons de scénarios, couverture par feature. advisor-agent.py release vote GO/NO-GO avant chaque push avec un score de confiance.

Le Quality Gate a 5 critères stricts :
• Pass Rate ≥ 95% · Fail Rate ≤ 5%
• Smoke 100% · Critical 100% · Couverture ≥ 80%

Un échec sur l'un des 5 bloque le merge automatiquement.

Q

Combien de temps pour intégrer le framework sur un projet client ?

• Framework Java : 1 semaine pour adapter le POM pattern, les step definitions, les properties
• Agents IA : 2 jours pour configurer les webhooks Slack/Jira et la clé Groq
• CI/CD : 1 jour pour adapter le workflow GitHub Actions ou GitLab CI

Total : 2 semaines pour un projet mid-size, framework opérationnel. Le plus long est toujours l'analyse des flows métier à couvrir — le code s'écrit vite.
Q

Tu fais quoi si le client utilise GitLab et pas GitHub ?

ci-agent.py appelle l'API GitHub Actions — il faut adapter les appels API (GitLab CI API). Le YAML de pipeline est différent mais la logique est identique. Estimation : une demi-journée pour migrer.

Les agents IA, eux, ne dépendent pas de la plateforme CI — ils lisent les fichiers JSON Allure en local. La couche CI est découplée des agents.

Questions Pièges — Comment les retourner

🪤

« Tu as testé sur QACart, une app de démo. Quelle est la différence avec une vraie app ? »

QACart est délibérément simple pour démontrer tous les patterns sans NDA ni accès confidentiel. La différence réelle sur un projet client : plus de pages, plus de step definitions, des iframes, des uploads, de l'authentification SSO.

Le framework est structuré pour ça — POM Pattern, TestContext ThreadLocal, EnvUtils multi-environnement. La complexité de l'app teste la solidité des fondations, pas leur existence.
🪤

« Les agents IA — si le LLM est coupé, vous faites quoi ? »

Le circuit breaker dans observability-agent.py gère exactement ce cas. Si Groq est indisponible, les agents tombent en mode dégradé : les tests s'exécutent normalement, les résultats sont disponibles dans Allure, les agents affichent un warning.

Aucune dépendance critique au LLM — il augmente le workflow humain, il ne le remplace pas.
🪤

« 100% pass rate c'est suspect — vous ne testez pas les cas d'échec ? »

Au contraire : 22 scénarios sur 34 sont des cas négatifs — mauvais mot de passe, email invalide, champs vides, suppression d'un item inexistant. 100% pass rate signifie que les 22 cas négatifs lèvent bien les bonnes erreurs ou comportements attendus.

Si l'app retourne un code 200 sur un login avec mauvais mdp, le test échoue — le pass rate refléterait un bug, pas notre complaisance.
🪤

« Pourquoi pas de tests de performance ? De sécurité ? »

Ce framework couvre le périmètre UI E2E fonctionnel — le scope délibérément défini. Les tests de performance (Gatling, k6) et sécurité (OWASP ZAP) sont des couches séparées avec leurs propres outils et pipelines.

Un framework qui essaie de tout faire fait tout mal. Je peux concevoir la couche performance ou sécurité séparément — c'est un choix d'architecture, pas une lacune.
🪤

« La connexion à une vraie base de données pour les fixtures — vous ne le faites pas ? »

Je le fais dès qu'on m'en donne l'accès. Le pattern est clair : au lieu d'un POST /api/register, on fait directement un INSERT INTO users via JDBC (PostgreSQL) ou MongoDB driver sync.

Sur QACart, la base MongoDB est privée — c'est une limite de l'app de démo. En mission client, j'ai les credentials DB, j'ajoute DbClient.java avec insertUser(), deleteUser(), userExists(), et le @Before/@After s'en charge. Estimation : 2 heures d'implémentation.

Les 5 Différenciateurs à marteler

Ces 5 points distinguent ton framework d'un "Selenium basique". Répète-les à chaque occasion — c'est ce dont le client se souvient.
01 🚀
API Setup Pattern
Les préconditions ne passent jamais par l'UI signup. Isolation totale — si le signup casse, les autres tests continuent.
« C'est le signe distinctif d'un QA Senior. »
02 🧠
Agents IA Multi-Patterns
6 patterns LLM différents selon le niveau de fiabilité requis. Pas un seul appel LLM naïf — une architecture de décision.
« Chain-of-Thought pour le RCA, Self-Consistency pour le flaky. »
03 📊
KPIs Auto-générés Allure
EnvironmentWriter calcule 18 KPIs depuis ISuiteResult et les écrit dans Allure. Zéro configuration manuelle, zéro plugin.
« Widgets Environment, Categories, Trend alimentés automatiquement. »
04 🔄
Retry Sans Annotation
IAnnotationTransformer injecte le retry sur tous les tests via META-INF/services. Le runner n'est jamais modifié.
« Auto-discovery TestNG — extensible sans toucher le code existant. »
05 🛡️
Circuit Breaker + Observabilité LLM
Traces des coûts, latences et erreurs LLM. Si Groq tombe, le framework continue en mode dégradé automatiquement.
« Résilience by design — jamais de point de défaillance unique. »
