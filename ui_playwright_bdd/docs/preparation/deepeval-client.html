DeepEval

Mesurer la qualité des réponses IA à partir de questions, de preuves et de critères explicites.

Présentation client · Version 1.0 · 1 octobre 2026

Exécution à la demande : DeepEval complète les tests Playwright/Cucumber. Il ne s’exécute pas après chaque réponse et n’autorise aucune release. Le générateur utilise lui aussi le gateway commun.

Définition des blocs · Entrées et préparation

Construire les cas à évaluer

01 · Dataset de référence

Contient les questions QA et les réponses attendues. Le dataset livré comprend quatre cas marqués DRAFT : les références et les seuils doivent être validés avec les experts métier.

evaluation/deepeval/dataset.json

02 · Orchestrateur Node

Prépare les paramètres, crée un identifiant d’exécution, collecte les cas puis lance DeepEval dans un environnement Python isolé. Il vérifie la version installée et impose un délai maximal de 15 minutes au processus d’évaluation.

scripts/deepeval.js · .venv-deepeval

03 · Recherche RAG

Retrouve des extraits utiles par recherche hybride ou BM25. Le mode hybride strict et top-k = 4 sont les valeurs par défaut. Une recherche inexploitable ou un corpus modifié pendant la collecte produit une erreur, pas un score.

shared/hybrid-rag.js · shared/rag.js

04 · Générateur LLM

Produit la réponse à évaluer à partir des extraits sélectionnés. Il utilise le client partagé et ses contrôles. Générer une réponse et la juger sont deux fonctions distinctes, même si elles peuvent utiliser le même modèle.

scripts/agents/llm.js

05 · Sorties existantes et captures

L’option --input charge des réponses déjà produites, sans nouvelle recherche ni génération. Une capture optionnelle des agents est disponible sur le chemin du circuit breaker Groq, y compris le cache ; elle ne couvre pas le secours Ollama hors de ce chemin.

scripts/capture-agent-eval.js

06 · Échantillons et manifeste

samples.json contient question, réponse, contexte de recherche et référence éventuelle. manifest.json identifie l’exécution, les réglages et l’empreinte du fichier. Le contexte collecté peut différer du texte transmis après masquage par le gateway : les scores doivent tenir compte de ce traitement.

logs/deepeval/<identifiant>/samples.json · manifest.json

Définition des blocs · Jugement et restitution

Évaluer et rendre le résultat traçable

07 · Moteur DeepEval Python

DeepEval 4.2.6 valide les échantillons, crée les cas LLMTestCase et mesure les critères sélectionnés de manière séquentielle. Chaque métrique fournit un score, un statut et une justification. Une erreur technique reste une erreur.

evaluation/deepeval/evaluate.py

08 · Adaptateur du juge Python / Node

FrameworkJudge envoie le prompt et le schéma JSON au processus Node. Le client Node appelle le fournisseur configuré ; Python valide la réponse structurée avec Pydantic. Le budget est de 30 appels logiques par défaut ; un cas peut demander plusieurs appels.

evaluation/deepeval/judge.py · scripts/deepeval-judge.js

09 · Gateway et transport mesuré

Le gateway contrôle le contenu, la destination, TLS, le modèle et les quotas avant le réseau. Le transport mesure les appels autorisés. Les refus de sécurité bloquent la requête ; ils ne déclenchent pas de changement de fournisseur.

shared/ai-gateway.js · shared/task-metrics.js

10 · LLM juge

Groq ou Ollama évalue les réponses à partir des consignes des métriques. Le fournisseur et le modèle sont configurables. Le juge ne dispose pas de secours fournisseur ; le client Groq désactive les reprises automatiques du SDK. Choisir un juge local ne rend pas le générateur local.

DEEPEVAL_JUDGE_PROVIDER · DEEPEVAL_JUDGE_MODEL

11 · Rapports et statut

report.html présente les résultats ; report.json expose scores, seuils, raisons, durées et statut global. error.json fournit un diagnostic si Python échoue avant le rapport. Le champ releaseAuthorized reste false.

logs/deepeval/<identifiant>/

12 · Métriques opérationnelles

Les appels du juge sont classés evaluation, les réponses produites generation et la recherche vectorielle embedding. L’identifiant de tâche relie les mesures à l’exécution. Les coûts sont estimés lorsque les tarifs sont connus.

logs/metrics/report.html · npm.cmd run metrics:report

Critères · Exploitation et limites

Lire les scores correctement

MétriqueQuestion évaluéeDéfaut
FaithfulnessLes affirmations sont-elles soutenues par le contexte ?Oui
Answer relevancyLa réponse répond-elle à la question ?Oui
Contextual precisionLes extraits utiles sont-ils bien classés ?Non
Contextual recallLe contexte couvre-t-il les informations attendues ?Non

Les deux métriques contextuelles exigent une réponse attendue. Paramètres par défaut : 2 cas, top-k 4, seuil 0,7 et 30 appels au juge. Le seuil est à calibrer avec le métier.

Codes de sortie

0 · PASS : métriques réussies.
1 · FAIL : au moins un score insuffisant.
2 · ERROR : erreur technique ou données invalides.

Délais du juge

Processus Node limité à 100 s par appel depuis Python ; client Groq à 90 s. Le gateway applique aussi sa limite de transport. Espacement facultatif entre appels : 0 à 60 s.

Commandes usuelles

npm.cmd run eval:deepeval:check
npm.cmd run eval:deepeval -- --limit 2
npm.cmd run eval:deepeval -- --input chemin/samples.json --limit 1
npm.cmd run metrics:report

Limites et confidentialité

  • Le juge LLM peut se tromper. Utiliser le même modèle pour générer et juger peut introduire un biais ; la revue humaine reste nécessaire.
  • La collecte standard évalue le RAG sur des questions QA. Elle ne mesure pas automatiquement toutes les décisions finales de tous les agents.
  • Rapports et échantillons restent locaux, mais peuvent contenir des données du projet. Ils ne sont pas nettoyés rétroactivement.
  • Avec Groq, les données nécessaires au jugement sont envoyées après les contrôles du gateway. La télémétrie DeepEval est désactivée et aucune publication Confident AI n’est déclenchée.
Un résultat PASS mesure les critères évalués sur les cas sélectionnés. Il ne prouve ni la conformité globale du système ni son aptitude à une mise en production.
