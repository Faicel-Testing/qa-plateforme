03 / LE SOCLE BDD

Du langage métier à la preuve

Exemple pédagogique : vérifier qu’une tâche créée est visible dans la liste.

Feature / scénario

Un fichier .feature décrit un comportement attendu avec Given, When, Then.

Exemple : une tâche saisie doit apparaître.

src/features/

Step definition

Une fonction TypeScript associée à une phrase Gherkin.

Elle orchestre les actions et vérifications.

src/steps/

Page Object

Classe qui regroupe les interactions avec une page.

Un changement de sélecteur est centralisé.

src/pages/

World

Objet contenant l’état d’un scénario : page, contexte navigateur, données.

Il évite le partage accidentel d’état entre scénarios.

src/core/world.ts

Hooks

Fonctions Before et After exécutées autour des scénarios.

Préparation, preuves, diagnostic et nettoyage.

src/hooks/hooks.ts

Assertion

Comparaison entre résultat observé et résultat attendu.

Exemple : vérifier qu’un élément est visible.

Playwright expect
À expliquer : « Cucumber trouve la fonction associée à la phrase. Le step utilise un Page Object. Playwright agit sur le navigateur, puis une assertion vérifie le résultat. »
Distinction essentielle : le runner de ce projet UI est CucumberJS. Playwright est utilisé pour l’automatisation et les assertions. Ne pas présenter ce projet comme une suite pilotée par le runner Playwright Test.

07 / LE RAG

Rechercher avant de répondre

RAG = Retrieval-Augmented Generation : génération enrichie par des informations retrouvées dans un corpus.

SourcesConnaissances, specs et features
ChunksExtraits découpés par lignes
RechercheBM25 et embeddings
Fusion RRFCombine les classements
RerankingReclassement si activé
Top-k + budgetSélection finale du contexte

BM25

Recherche lexicale : valorise les correspondances de mots.

Utile pour un nom de test ou une erreur exacte.

Embedding

Vecteur numérique représentant le contenu d’un extrait.

La similarité aide à retrouver un sens proche ; embeddings via Ollama.

RRF

Reciprocal Rank Fusion : combine les positions de plusieurs classements.

Associe recherche lexicale et sémantique.

Reranking

Un modèle réévalue la pertinence des extraits candidats.

Optionnel ; peut envoyer les extraits à Groq.

Top-k

Nombre maximal d’extraits à retenir dans le contexte.

4 par défaut ; le budget peut réduire le nombre réellement transmis.

Provenance

Chemin, lignes et empreinte permettent de retrouver les sources.

Les épisodes IA restent non vérifiés ; les vecteurs sont stockés localement.

Le RAG améliore l’accès au contexte ; il ne garantit pas l’exactitude. La documentation du module exclut notamment les .env et les logs bruts de l’index.

08 / CHUNKS

Un document devient des extraits traçables

Chunk = fragment de texte utilisé comme unité de recherche. Ce n’est ni un token, ni un embedding.

Document sourceTexte lu depuis le corpus autorisé
DécoupageRegroupe les lignes entières
ChunksFragments de 1 800 caractères maximum
IndexTermes BM25 et vecteurs associés

Pourquoi découper ?

Retrouver un passage pertinent sans transmettre un document complet au modèle.

Un même document peut fournir plusieurs chunks.

Comment dans ce code ?

chunkFile() accumule les lignes jusqu’à la limite de 1 800 caractères.

Pas de chevauchement explicite. Une ligne trop longue est omise et signalée.

scripts/agents/shared/rag.js

Que conserve un chunk ?

Texte, identifiant, chemin, lignes de début et de fin, empreinte de la source et type.

Ces métadonnées permettent de retrouver et vérifier l’extrait.

Chunk et embedding

Le chunk est du texte lisible ; l’embedding est sa représentation numérique.

Le vecteur aide à chercher. Le texte retenu constitue le contexte du LLM.

Taille et compromis

Un fragment court cible mieux un passage, mais peut perdre du contexte.

Un fragment long contient plus de contexte, mais peut ajouter du bruit.

Cas de la mémoire IA

Le découpage traite séparément les lignes d’épisodes sélectionnés.

L’historique reste identifié comme non vérifié, même après indexation.

À dire au client : « Je découpe les sources en passages identifiables. Le RAG retrouve ces passages et conserve leur provenance pour permettre la vérification. »

09 / TOP-K

Combien de chunks envoyer au modèle ?

Top-k = plafond du nombre d’extraits sélectionnés après classement. Le budget de contexte s’applique aussi.

Chunks candidatsRésultats BM25 et sémantiques
ClassementFusion RRF puis reranking si activé
SélectionAu plus k chunks qui tiennent dans le budget
LLMReçoit les textes et leurs références

Exemple fictif : k = 4

C1Règle métier de connexionRETENU
C2Scénario de connexion existantRETENU
C3Précondition du compte de testRETENU
C4Note QA sur le message attenduRETENU
C5Ancienne analyse peu pertinenteNON RETENU
C6Règle de suppression sans rapportNON RETENU

Illustration uniquement : ces six extraits ne proviennent pas d’une recherche exécutée. On suppose que les quatre premiers tiennent dans le budget.

Valeurs par défaut du code

topK = 4 et maxChars = 4 500.

Le coût utilisé est la longueur du chunk sérialisé en JSON, métadonnées comprises. Ce ne sont pas 4 500 tokens.

rag.js : selectHits() ; hybrid-rag.js : search()

Pourquoi moins de quatre ?

Le corpus peut être insuffisant ou le budget ne pas permettre de retenir quatre chunks.

Un extrait qui dépasse le budget restant est sauté ; la sélection peut en retenir un suivant plus petit.

Ne pas confondre

k est le nombre maximal de chunks, pas le nombre de documents ou de réponses du LLM.

La limite de candidats du reranker est une étape distincte du top-k final.

À dire au client : « Je classe les chunks, puis je sélectionne au maximum quatre extraits dans le budget prévu. Augmenter k peut enrichir le contexte, mais aussi ajouter du bruit et de la consommation. »

12 / PREUVES ET ÉVALUATION

Mesurer les tests et mesurer l’IA

Deux objets différents : le comportement de l’application et la qualité des réponses des modèles.

Allure

Rapport de tests avec statuts et pièces jointes.

Un rapport peut être partiel ; sa présence ne signifie pas réussite.

Traces et captures

Éléments pour reconstituer un échec navigateur.

Les hooks collectent les informations selon les conditions du run.

Manifeste de run

Identifie l’exécution et conserve sa complétude et son code de sortie.

Évite d’utiliser de vieux résultats comme preuve nouvelle.

Métriques IA

Durée, consommation et coûts estimés des appels.

Un tarif inconnu ne doit pas devenir un coût nul.

DeepEval

Évalue les réponses IA sur un jeu de cas et leur contexte.

Lancé à la demande, dans un environnement Python séparé.

Fidélité / pertinence

Fidélité : appui sur le contexte. Pertinence : réponse à la question.

Ces scores ne prouvent pas la conformité de l’application.

DeepEval ne juge pas automatiquement chaque réponse de chaque agent. Ses résultats dépendent du jeu de référence, du contexte fourni et du juge.

14 / ENTRAÎNEMENT

Les questions probables du client

Dans la version HTML, cliquez sur une question pour révéler la réponse. Dans le PDF, toutes les réponses sont visibles.

Pourquoi Cucumber et Playwright ?

Cucumber relie les scénarios métier aux steps. Playwright exécute les actions navigateur et fournit les assertions.

Agent, modèle et harness : quelle différence ?

L’agent porte une tâche QA. Le modèle génère une réponse. Le harness prépare, encadre et observe l’utilisation du modèle.

Comment vérifiez-vous le code généré ?

Par des contrôles de syntaxe, de types selon le chemin utilisé, une revue métier et une exécution. Aucun de ces contrôles seul ne suffit.

Le RAG évite-t-il les hallucinations ?

Il fournit des sources pertinentes et traçables, mais une réponse peut encore être fausse. Je vérifie ses références et ses conclusions.

Qui décide du GO / NO-GO ?

Advisor formule une recommandation et un gate. La décision doit respecter les preuves, les blocages techniques et la gouvernance humaine applicable.

Le framework répare-t-il tout seul ?

Un mode de réparation existe, mais le pipeline full consulté lance bug analyze. Je ne promets pas une réparation automatique de tous les échecs.

Que se passe-t-il si le LLM est indisponible ?

Les mécanismes de résilience et les erreurs sont gérés selon le chemin d’appel. Le Runner peut lancer Cucumber sans attendre un résumé IA.

Tout est-il branché à la CI ?

La CI UI lance Cucumber/Playwright et Allure. Le pipeline complet des agents constitue actuellement un autre chemin.

Si un détail vous échappe : « Je préfère vérifier le chemin d’exécution dans le code. Je peux vous montrer le module qui le gère. »

15 / VOTRE PRÉSENTATION

Un pitch de 60 secondes

L’objectif : expliquer le parcours d’un test et situer l’IA avec précision.

« Mon framework UI repose sur Cucumber, Playwright et TypeScript. Les features décrivent les comportements métier ; les steps s’appuient sur des Page Objects et un contexte isolé par scénario. Les assertions et les preuves Allure permettent d’analyser le résultat.

J’ai ajouté une couche d’agents pour la préparation, l’analyse des échecs et les recommandations. Leur LLM harness rassemble le contexte documentaire, les appels aux modèles, les contrôles, la résilience et les métriques.

Je distingue toujours une proposition IA d’un résultat démontré : je vérifie les sources, le code et les tests, et je conserve les validations QA nécessaires. »

À montrer en premier

Une feature, son step, son Page Object et l’assertion associée.

Expliquez ce parcours avant les agents.

À montrer ensuite

Un rapport avec les preuves, puis le rôle du harness.

Partez d’un exemple concret d’échec.

À éviter

Promettre une IA autonome et infaillible ou une couverture totale.

Distinguez code présent, configuration et exécution prouvée.
